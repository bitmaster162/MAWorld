# 2. Canonical Language Boundary

The report proposes:

> Rust decides and stores truth; Python proposes.

This is directionally useful but too broad as a system invariant.

The canonical rule is:

```text
Authority comes from service ownership, policy, credentials, and contracts.
It does not come from the implementation language.
```

Recommended default:

## Rust

Prefer Rust for components where failure can corrupt identity, integrity,
idempotency, or authoritative mutations:

- streaming SHA-256 ingestion;
- content-addressed storage;
- no-overwrite CAS writes;
- artifact identity;
- canonical JSON hashing;
- deterministic contract validation;
- high-integrity ingestion API;
- policy-critical adapters where Rust materially improves assurance;
- later Trading Cell deterministic components.

## PostgreSQL

PostgreSQL remains the authoritative transactional state for:

- artifact/source metadata;
- project isolation;
- provenance relationships;
- claims and evidence;
- canonical decisions;
- workflow metadata;
- RLS enforcement.

Rust does not “store truth” by itself. The Rust service is the controlled writer
and validator for authoritative PostgreSQL/object-store state.

## Python

Python remains valid for non-authoritative or model/IO-bound workloads:

- document parsing;
- OCR fallback;
- LLM claim extraction;
- embedding generation;
- semantic duplicate candidates;
- contradiction candidates;
- evaluation;
- research workflows;
- notebooks;
- migration utilities;
- orchestration adapters.

Python outputs remain:

```text
PROPOSED / CANDIDATE / UNVERIFIED
```

until validated and committed by the authoritative service path.

Python is not prohibited from deterministic tasks. It is prohibited from bypassing
the authoritative contracts and policy boundary.

# 3. Intake Domain Model — Accepted Correction

The following separation is promoted to candidate canon:

```text
RawBlob
Occurrence
LogicalDocument
ArtifactVersion
```

## RawBlob

Represents immutable bytes.

Key properties:

- `sha256`;
- `byte_size`;
- `storage_key`;
- `created_at`;
- exact-byte recovery;
- never overwritten.

## Occurrence

Represents where and when the same content was observed.

Key properties:

- source system;
- native source ID;
- source path/URI;
- observed timestamp;
- source-created/modified timestamps;
- project scope;
- access policy;
- deletion observation.

One RawBlob may have many Occurrences.

## LogicalDocument

Represents the project-level identity of a work across:

- renames;
- copies;
- format conversions;
- exports;
- editions.

## ArtifactVersion

Represents an explicit version or derivative of a LogicalDocument.

This resolves the previous ambiguity between byte identity, source identity,
document identity, and version identity.

# 4. Content-Addressed Storage

## Decision

Adopt a no-overwrite SHA-256 content-addressed store behind `ObjectStore`.

Candidate implementation:

- write to a temporary path;
- stream SHA-256 while receiving bytes;
- fsync where required;
- atomically link or rename into the hash path;
- never overwrite existing content;
- compare size/hash on collision;
- return the existing RawBlob for an identical hash.

## Hard-Link Caveat

A hard-link-based no-overwrite strategy is valid only when:

- temporary and final paths are on the same filesystem;
- the filesystem supports hard links;
- Windows behavior is tested;
- network filesystems are excluded or explicitly tested.

The `ObjectStore` contract must not depend on hard links.

Implementations:

- `LocalCasStore`;
- later `S3ObjectStore` / `MinioObjectStore`.

  `serde_json_canonicalizer`.

3. Test duplicate-key handling.
4. Test negative zero and exponent forms.
5. Create cross-language fixtures:
   - Rust;
   - Python;
   - JavaScript/TypeScript.
6. Store canonicalization profile/version with every digest.

Canonical object hash contract:

```text
schema_id
+ schema_version
+ canonicalization_profile
+ canonical_bytes
→ SHA-256 digest
```

Do not hash arbitrary JSON serialization.

# 6. PostgreSQL and sqlx

## Direction

`sqlx` is a strong candidate because it supports:

- async PostgreSQL;
- typed query mapping;
- compile-time/offline query verification;
- migrations;
- integration with Rust services.

## Constraint

Compile-time SQL validation is only real when:

- `DATABASE_URL` is available during query preparation; or
- `.sqlx` offline metadata is generated and committed.

Required CI:

```text
sqlx migrate run
cargo sqlx prepare --check
cargo test
```

Do not claim compile-time query safety without a prepared schema and CI check.

## pgvector

pgvector support is not required for the first intake slice.

The Rust authority core should not depend on semantic indexing.

Embedding jobs may be implemented separately and update derived tables.

# 7. RLS Correction

The Claude report proposes `FORCE ROW LEVEL SECURITY` from day one.

Direction accepted, but project isolation must be proven.

Required design:

- a request-scoped database transaction;
- set a trusted project/actor context inside the transaction;
- no connection returned to pool with stale session state;
- service role must not silently bypass RLS;
- migration/admin role separated from runtime role;
- background workers receive explicit project scope;
- RawBlob access derives from authorized Occurrence/project relations.

Required tests:

1. Project A cannot query Project B occurrences.
2. Shared RawBlob bytes are inaccessible without an authorized occurrence.
3. Connection-pool reuse does not leak prior project context.
4. Background job cannot process another project without capability.
5. Owner/admin bypass is separately audited.
6. Deleted occurrence does not expose blob through orphaned relation.
7. SQL injection cannot modify the request-scoped project identity.

Use `SET LOCAL` or an equivalent transaction-scoped mechanism rather than
unbounded session state.

The report claims a verifiable audit hash-chain in the standalone Rust slice.

Canonical status:

```text
ACCEPT AS SPIKE PATTERN
```

It does not replace the ContinuityOS authoritative audit design until integrated.

Required event digest:

```text
event_hash =
SHA256(
  previous_hash
  + canonical_event_payload
  + sequence
  + event_type
  + timestamp
)
```

Required properties:

- monotonic sequence;
- no parallel forked heads;
- canonical payload profile;
- verification command;
- corruption fixture;
- replayable test;
- link to workflow/action/proposal IDs.

For PostgreSQL concurrency, choose one:

- one serialized ledger-writer process;
- transactional advisory locking;
- partitioned chains with signed checkpoints.

Do not introduce complex external anchoring in the intake MVP.
